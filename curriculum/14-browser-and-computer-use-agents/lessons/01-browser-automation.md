# Browser automation

**Last verified:** 2026-09-22
**Difficulty:** ★★★★☆ · **Time:** ~45 minutes

## Learning objectives

- Give a browser-automation agent a small, typed action vocabulary (`goto`, `click`, `get_text`) instead of arbitrary browser control.
- Scope navigation to an explicit URL allowlist, the same least-privilege discipline as Module 13's sandboxing.
- Explain why DOM/selector-based automation (this lesson) is more reliable than pixel-based control for tasks confined to a browser.

## Intuition

A web page is structured data (the DOM) with a visual rendering on top of
it. Playwright -- the current, actively maintained standard for
Python browser automation (verified against playwright.dev on 2026-09-22)
-- lets an agent interact with that structure directly: "click the element
matching this CSS selector," not "click the pixel at (640, 480)." This is
categorically more reliable than pixel-coordinate control whenever the task
is confined to a browser, because selectors survive layout changes that
would silently break fixed coordinates.

## The concept

### A small, typed action vocabulary

Following the same principle as Module 13's narrow toolset (only the file
operations a coding agent's specific task needs), this module's lab exposes
exactly three actions:

```python
class BrowserSession(Protocol):
    def goto(self, url: str) -> None: ...
    def click(self, selector: str) -> None: ...
    def get_text(self, selector: str) -> str: ...
```

A real backing implementation wraps a Playwright `Page`:

```python
class PlaywrightBrowserSession:
    def __init__(self, page):
        self._page = page

    def goto(self, url: str) -> None:
        self._page.goto(url)

    def click(self, selector: str) -> None:
        self._page.click(selector)

    def get_text(self, selector: str) -> str:
        return self._page.text_content(selector) or ""
```

`BrowserSession` being a `Protocol` (structural typing, not inheritance) is
what makes this lab offline-testable without a real browser at all: any
object with these three methods works, including a small hand-written fake
used in tests -- the same idea as `shared/llm/mock.py`'s `MockLLMProvider`
standing in for a real provider.

### URL allowlisting is the browser equivalent of Module 13's path-scoping

```python
def goto(session: BrowserSession, url: str, allowed_prefixes: tuple[str, ...]) -> str:
    if not any(url.startswith(prefix) for prefix in allowed_prefixes):
        raise ValueError(f"URL not allowed: {url!r}")
    session.goto(url)
    return f"Navigated to {url}"
```

Exactly like Module 13's `resolve_within_repo` rejecting paths outside a
repo root, `goto` rejects any URL the task didn't explicitly authorize --
without this, a model that decides to "look something up" mid-task could
navigate anywhere, including sites designed to feed it malicious instructions
(Module 18 covers this as indirect prompt injection via untrusted page
content -- allowlisting where the agent can even go is the first line of
defense, before content-level defenses are even relevant).

## Deeper: this only works because the task stays inside a browser

DOM-based automation's reliability advantage is specific to browser tasks.
The moment a task needs to interact with a native desktop application, a PDF
viewer, or anything outside the browser's own DOM, selectors don't apply --
that's exactly the gap general computer-use tools (lesson 02) fill, at the
cost of the reliability this lesson's approach provides.

## When not to use this

Don't reach for full browser automation when a task only needs to read a
page's content once -- a plain HTTP GET (Module 00's async-fetch-cli, or
Module 06's retrieval tools) is far cheaper and more reliable than launching
a browser for something that doesn't require rendering or interaction.

## Common mistakes

- Using brittle selectors (deeply nested CSS paths generated by a browser's
  "copy selector" feature) instead of stable ones (an element's `id`, or a
  dedicated test attribute) -- the former breaks on minor markup changes
  unrelated to the task.
- Giving the agent a generic "run this Playwright code" tool instead of a
  small fixed action vocabulary -- this reopens the same "arbitrary
  generated code" risk Module 13 lesson 01 sandboxes against, now for
  browser automation.
- No URL allowlist, on the assumption that "the task only needs one site
  anyway" -- until the model reasons its way into visiting a different one.

## Key takeaways

- Playwright's selector-based automation is the current standard for reliable, DOM-based browser control.
- A small, typed action vocabulary (goto/click/get_text) plus a URL allowlist mirrors Module 13's file-scoping discipline, applied to browsing.
- DOM-based reliability is specific to in-browser tasks -- it doesn't extend to interacting with anything outside the browser's own structure.
