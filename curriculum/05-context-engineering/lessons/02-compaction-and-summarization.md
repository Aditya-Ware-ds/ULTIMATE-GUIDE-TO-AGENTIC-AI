# Compaction and summarization

**Last verified:** 2026-09-22
**Difficulty:** ★★★★☆ · **Time:** ~1 hour

## Learning objectives

- Implement a compaction strategy that keeps a growing conversation under a token budget.
- Compare truncation, summarization, and sliding-window strategies and know when each fits.
- Explain what's lost with each strategy, so you can pick deliberately rather than by default.

## Intuition

An agent that runs for many steps (Module 04) accumulates history forever
unless something actively shrinks it. **Compaction** is the general term for
that shrinking: replacing some of the accumulated conversation with a smaller
representation that preserves what still matters, so the agent can keep running
without exceeding its context budget (or degrading from it -- lesson 03).

## The concept

### Three strategies, in increasing order of sophistication

1. **Truncation** -- simply drop the oldest messages once you're over budget.
   Cheapest to implement, but loses information outright -- fine when old turns
   are genuinely no longer relevant (e.g. a long back-and-forth that resolved a
   sub-question whose answer is already reflected in a later message).
2. **Sliding window** -- keep the system prompt plus only the most recent N
   messages, dropping everything older unconditionally. Simple and bounded, but
   can lose information from steps ago that's still needed (e.g. an early tool
   result the agent needs to reference again at step 15).
3. **Summarization** -- replace a block of older messages with a short
   model-generated (or programmatically-generated) summary that preserves the
   gist while using far fewer tokens. More expensive (an extra model call, for
   real summarization) but preserves more of what matters than truncation alone.

### A minimal compaction function

```python
from shared.llm.types import Message, Role


def compact_messages(
    messages: list[Message], max_tokens: int, count_tokens, keep_recent: int = 4
) -> list[Message]:
    if count_tokens(messages) <= max_tokens:
        return messages

    system_messages = [m for m in messages if m.role == Role.SYSTEM]
    rest = [m for m in messages if m.role != Role.SYSTEM]
    recent = rest[-keep_recent:]
    older = rest[:-keep_recent]

    if not older:
        return messages  # nothing left to compact

    summary = Message(
        role=Role.USER,
        content=f"[{len(older)} earlier messages omitted to stay within the context budget.]",
    )
    return [*system_messages, summary, *recent]
```

This always preserves the system prompt and the most recent `keep_recent`
messages (the ones most likely to still matter to the immediate next step),
and collapses everything older into one placeholder. A production system would
replace that placeholder with a real summary generated by an extra model call
-- the *mechanism* (shrink old content, keep recent content and the system
prompt intact) is what this lesson and its lab teach; generating a *good*
summary is itself a prompting problem (Module 02, lesson 04).

### When to trigger compaction

Check the token budget *before* each model call (not after, when it's too
late), using a real or estimated token count (Module 01, lesson 01) of the full
`messages` list you're about to send.

## Deeper: compaction is lossy, and that's the whole trade-off

Every compaction strategy discards some information -- the entire point is
trading completeness for staying within budget (and, per lesson 03, for
maintaining quality). The real design question isn't "how do I avoid losing
information" (impossible, given a fixed budget and unbounded history) but "what
information can I afford to lose, and when." An agent doing long-horizon work
that must remember specific facts from far in the past needs a different
solution entirely -- persistent memory (Module 07), not compaction, which is
fundamentally about the *current conversation's* context window, not
durable state across runs.

## When not to use this

Don't compact a short conversation that's nowhere near its budget -- compaction
itself costs something (a placeholder loses fidelity; real summarization costs
an extra model call), so only pay that cost when you're actually approaching
the budget.

## Common mistakes

- Compacting *after* sending an over-budget request instead of checking before
  -- by then the call has already failed or degraded.
- Dropping the system prompt during compaction -- it should almost always
  survive every compaction pass; losing it mid-conversation changes the model's
  behavior unpredictably.
- Using truncation/sliding-window when the task genuinely needs specific facts
  from early in a long conversation -- that's a sign you need retrieval or
  persistent memory (Module 06/07), not more aggressive compaction.

## Key takeaways

- Truncation, sliding windows, and summarization trade implementation cost against how much useful information survives compaction.
- Always preserve the system prompt and check the token budget before each call, not after.
- Compaction manages the current conversation's context window; it isn't a substitute for persistent memory across separate runs (Module 07).
